# Live Alerts (windows/alerts): How It Works

*Living doc. v6, 2026-11-20. Tested end to end on Server 2022 (domain controller): self-test **25 PASS / 1 FAIL**; the FAIL was a real finding (Guest enabled). Member-server path not yet tested on real hardware (see Test status).*

Four PowerShell scripts that install into `C:\bt` on any Windows box with one paste:

| Script | Job | Changes the box? |
|---|---|---|
| `bt-alerts.ps1` | Instant alerts when someone logs in, creates users, adds admins, plants persistence. Tells you **who, from where, how**, and the commands to undo it | Yes: audit policy, log size, scheduled tasks (all reversible) |
| `whoshere.ps1` | "Is anyone else on this box?" on one screen, plus a "what's new since my baseline" diff | No (read-only; writes `C:\bt\baseline.xml`) |
| `pii-hunt.ps1` | Finds card numbers, SSNs, national IDs and passwords in files, shares and SQL Server | No (read-only; writes `C:\bt\pii-report.txt`) |
| `bt-selftest.ps1` | Fires every detection for real, checks each one alerted, reports PASS/FAIL with a diagnosis, cleans up | Temporarily (throwaway user, task and service, all removed) |

Deploy, either way:
- **From the repo:** panel `[D] LIVE ALERTS` → `[1] Install`. It copies the four scripts to `C:\bt` and installs.
- **Box with no repo (RDP clipboard / console only):** open **Admin PowerShell** (on Server Core type `powershell` first), paste `windows/alerts/bt-deploy-PASTE.txt`, press Enter.

The bundle is deliberately **standalone**: it does not use `windows/lib/CCDC-Common.ps1` and keeps its own folder `C:\bt`, so a single paste works on a box with nothing else on it. `bt-deploy-PASTE.txt` is generated by `tools/build-alert-paste.py`; never edit it by hand.

## 1. Compatibility

| Works on | Why |
|---|---|
| Windows Server 2012 R2, 2016, 2019, 2022, 2025 | Every command used exists in PowerShell 4+, the default on 2012 R2 |
| Windows 8.1 / 10 / 11 (Pro, Enterprise, Home) | Same. Home has no `msg.exe`/`query.exe`, so those features are skipped, not crashed |
| Domain controller, member server, standalone | The scripts read `Win32_ComputerSystem.DomainRole` and choose AD or local commands accordingly |
| GUI **and** Server Core | No sound or GUI dependencies: alerts are a `msg.exe` popup (if present) and plain text in the watch window |
| RDP, console, SSH, WinRM sessions | Over SSH/WinRM the install doesn't open a window and tells you to run `-Watch` in that session |
| **Any Windows language** | Audit policy is set by **GUID**; privileged groups, Guests and Guest are matched by **well-known SID**, never by English name |

**Not supported:** Server 2008 R2 / Windows 7 (PowerShell 2.0 has no `Register-ScheduledTask` or CIM cmdlets).

**Portability rules the code follows:** no hard-coded IPs, domains, hosts or account names; no built-in alias names reused as function names (`h` = `Get-History` broke an early version); every optional command (`msg.exe`, `query.exe`, `Get-MpComputerStatus`, `Get-LocalGroupMember`, Defender's log) is checked before use.

## 2. bt-alerts.ps1

### 2.1 The core idea
Windows already writes an **event** to the Event Log for everything that matters: a logon (4624), a user created (4720), a group change (4728/4732/4756), a service installed (4697/7045), a task created (4698), the log cleared (1102).

Task Scheduler has a little-known trigger type, **"On an event"**: run a program the moment an event matching a filter is written. bt-alerts registers one task per detection. Each task watches for its event and runs `bt-alerts.ps1 -Key <name>` as SYSTEM within about a second.

```
Something happens -> Windows writes event 4720 -> Task "BT-Alert-usernew" sees it
  -> runs bt-alerts.ps1 -Key usernew -> reads that event -> traces who/where
  -> popup + log lines -> watch window prints it
```

Attackers use the same mechanism (event-triggered persistence, MITRE T1546). Here it's used for detection. Tomorrow, an "On an event" task **you** didn't create is a red flag.

### 2.2 What `-Install` does, step by step
1. **Copies itself** to `C:\bt\bt-alerts.ps1` and drops an "installing" flag (so deleting and recreating its own tasks doesn't trigger the tamper alert).
2. **Turns on seven audit-policy subcategories by GUID** (success + failure). Without these, Windows never writes most of the events:

   | GUID suffix | Subcategory | Needed for |
   |---|---|---|
   | `0CCE9215` | Logon | 4624 / 4625 |
   | `0CCE9235` | User Account Management | 4720 / 4722 / 4724 |
   | `0CCE9237` | Security Group Management | 4728 / 4732 / 4756 |
   | `0CCE9227` | Other Object Access Events | 4698 / 4699 (tasks) |
   | `0CCE9211` | Security System Extension | 4697 (service install with who/where) |
   | `0CCE9240` | Kerberos Service Ticket Ops | 4769 (Kerberoasting, DC) |
   | `0CCE922F` | Audit Policy Change | 4719 (auditing turned off) |

3. **Raises the Security log to 512 MB** if smaller, so "who/from where" lookups still find the original logon hours later.
4. **Auto-trusts your RDP source IP**: finds your latest type-10 logon and adds its IP to `C:\bt\trusted.txt`.
5. **Registers the alert tasks.** For each detection it builds an event subscription (XPath filter), then registers `BT-Alert-<key>`: runs as **SYSTEM**, highest privileges, 2-minute time limit. Noisy triggers use **IgnoreNew** (a burst of events can't spawn a pile of PowerShell processes); important ones use **Queue** (none are lost). It skips any trigger whose log doesn't exist (e.g. no Defender log) and records how many installed for the heartbeat.
6. **Runs the backfill** (section 2.6).
7. **Opens the watch window**, but only at an interactive desktop console.

### 2.3 The detections

| Key | Event (log) | Fires when | Noise control |
|---|---|---|---|
| `rdp` | 4624 type 10 (Security) | Anyone RDPs in | Same user + IP at most once / 5 min |
| `netlogon` | 4624 type 3, **NTLM only**, not from this box's own IPs | Network logon (SMB/WinRM/PsExec-style) | Skips machine accounts (`NAME$`) and trusted IPs; once / 10 min per user + IP. NTLM-only keeps busy DCs quiet (normal domain traffic is Kerberos; pass-the-hash, PsExec-by-IP and most spraying tools use NTLM) |
| `failed` | 4625 | 5+ failed logons from one IP within 2 min | Once / 5 min per IP |
| `kerberoast` (DC only) | 4769 with RC4 (`0x17`) | Service ticket requested with weak RC4 crypto | Skips computer accounts + krbtgt; once / 10 min |
| `usernew` | 4720 | User account created | — |
| `userenable` | 4722 | Account enabled | Skipped if within 5 s of that account's creation (part of creating it) |
| `pwreset` | 4724 | Password reset by someone else | Same 5 s creation rule |
| `groupadd` | 4728 / 4732 / 4756 | Member added to any security group | — |
| `svc4697` | 4697 (Security) | Service installed, **with who/where** | — |
| `svc7045` | 7045 (System) | Service installed (always logged, even without auditing) | Waits 3 s; stays quiet if the 4697 version fired |
| `logclear` | 1102 | Security log wiped | — |
| `defender` | 1116 / 1117 / 5001 / 5007 | Malware found, real-time protection off, settings changed | 5007 once / 2 min |
| `taskdel` | 4699 / 4702 | One of **your** `BT-Alert-*` tasks deleted, or changed to run other code | Ignored during install/remove; a 4702 that leaves the task enabled and pointing here is ignored |
| `auditoff` | 4719 | Audit policy "removed" on one of the 7 subcategories the alerts need | Looks at the whole burst; once / 10 min |
| `task` | 4698 | Scheduled task created; the alert shows **the command it runs** | Ignores its own tasks |

### 2.4 Who / from where / how: the Logon ID trace
Every action event (user created, group add, task, service, log cleared) records the **SubjectLogonId** of the session that did it. That ID matches the **TargetLogonId** of the original **4624 logon** event, which holds:
- **IpAddress**: where they came from
- **WorkstationName**: their computer name (e.g. `KALI`)
- **LogonType**: 2 console, 3 network, 10 RDP, and so on
- **AuthenticationPackageName**: NTLM / Kerberos / Negotiate

The script finds that logon with one XPath query and turns it into a plain-English **HOW** line:
- Type 3 + NTLM → "password **or stolen hash** (pass-the-hash), typical of SMB/PsExec/WinRM tools"
- Type 10 → "RDP with a valid password"
- Logon ID `0x3e7` → "**SYSTEM on this box**": a service, task, webshell or exploit already running locally, not a remote login

If the logon event has rolled out of the log or been cleared, the alert says so instead of guessing.

### 2.5 What an alert produces
1. **Center-screen popup** (`msg *`) on every logged-in session, up to 255 characters (a `msg.exe` limit). Skipped if `msg.exe` doesn't exist or popups are snoozed.
2. **One line** in `C:\bt\alerts.log`: time, box, title, what, who, from.
3. **A full block** in `C:\bt\alerts-full.log`: WHAT / WHO / FROM / LOGON / HOW / **DO NOW**.
4. Optional Discord webhook (**off** by default; leave it off unless Black Team says it's OK).

**DO NOW commands adapt to the box:**
- Disable an account: `Disable-ADAccount` on a DC; `net user <n> /domain /active:no` on a member server; `net user <n> /active:no` for local accounts.
- If the source IP isn't trusted: `-Block <ip>` (attacker) and `-Trust <ip>` (scorer/teammate) are added at the top.
- If the action came from a trusted IP (you), "disable the account that did this" is left out, so a panicked copy-paste can't lock out your own admin.

### 2.6 Backfill: what happened before you arrived
On install (or `-Backfill -Hours N`) it reads the last 24 h of the same events and prints five sections:
1. **Privileged group changes**: matched by SID (Domain/Enterprise/Schema Admins, GPCO, Administrators, Account/Server/Print/Backup Operators, Pre-Windows 2000, Remote Desktop / Remote Management Users) plus DnsAdmins by name
2. **Accounts created**: grouped by minute and creator
3. **Re-enabled / password reset**: excluding the steps that are part of account creation
4. **Services / tasks / log clearing**: Microsoft and driver services filtered out
5. **Logons from outside**: machine accounts and trusted IPs hidden, grouped with counts

Windows setup noise (`ANONYMOUS LOGON`, `SYSTEM`, machine accounts) is filtered out.

**Limits:** it only sees what Windows was already auditing. Default Windows doesn't log task creation, so tasks planted before install won't show. Services always show (System log). The backfill complements your persistence sweep; it doesn't replace it.

### 2.7 The watch window (`-Watch`)
- Reads new lines from `alerts-full.log` every second (shared read, so it never locks the file).
- Prints the whole alert block. No sound, nothing to acknowledge. The title bar shows the time of the last alert.
- **Heartbeat:** every 30 s it checks that the alerting is intact (see 2.11). Problems become an ALERTING TAMPERED alert.
- **QuickEdit is turned off for this window.** With it on, one mouse click pauses the whole window ("Select" in the title) until a key is pressed. To copy text: title bar right-click → Edit → Mark, drag, Enter. Or open `C:\bt\alerts-full.log` in Notepad from an Admin PowerShell.
- **One per box:** the newest window writes its PID to `C:\bt\watch.pid`; older windows notice within 30 s and close themselves (otherwise they would flag a redeploy as "script edited"). `-Install` also closes older ones it can find.
- Headless-safe: works over SSH/WinRM/Server Core (text only there).

The popup (`msg *`) closes by itself after 60 s. Sound was removed on purpose: it depends on the audio service and RDP settings, so it isn't reliable on every box.

### 2.8 Commands
| Command | Does |
|---|---|
| `-Install` | Everything in 2.2 (safe to re-run; replaces its tasks, keeps `trusted.txt`) |
| `-Watch` | Opens or reopens the watch window |
| `-Test` | Fake alert (popup + log + watch window) |
| `-Trust <ip>` | No more network-logon alerts from that IP |
| `-Block <ip>` | Windows Firewall block in + out (refuses trusted IPs; turns the firewall on) |
| `-Snooze <min>` | Mutes popups (still logged + shown) |
| `-Backfill [-Hours N]` | Re-runs the history report |
| `-Chain <ip> [-Hours N]` | Full story of one IP (see 2.12) |
| `-Remove` | Deletes all `BT-Alert-*` tasks |

### 2.9 Everything it changes, and how to undo it
| Change | Undo |
|---|---|
| Audit subcategories on | `auditpol /set /subcategory:"{GUID}" /success:disable /failure:disable` (harmless to leave on) |
| Security log 512 MB | `wevtutil sl Security /ms:<old bytes>` |
| `BT-Alert-*` tasks | `C:\bt\bt-alerts.ps1 -Remove` |
| `C:\bt` locked to Administrators + SYSTEM | `icacls C:\bt /reset /T` |
| `C:\bt` folder | Delete it (it's also your evidence; keep it until after reports) |
| Firewall rules from `-Block` | `Get-NetFirewallRule -DisplayName 'BT block*' \| Remove-NetFirewallRule` |

It never stops, restarts or modifies a scored service, and never changes passwords on its own.

### 2.10 Known limits
- **Kerberos-based attacker logons** don't trigger `netlogon` (NTLM-only, by design for overhead). Anything they *do* afterward still alerts with their source.
- **A domain GPO can override** the audit settings. If expected alerts don't come, `auditpol /get /category:*` shows what's active, and the self-test pinpoints it.
- **An attacker with admin rights can disable it.** The tamper alert and heartbeat make that loud, but they can't make it impossible.
- **Over SSH/WinRM**, popups don't reach you; the watch window text still does.

### 2.11 v6: tamper protection

Nothing stops an attacker with admin rights from breaking a tool on a box they control. v6 makes breaking it loud.

| Attack on the alerting | How v6 catches it |
|---|---|
| Delete an alert task | Event 4699 -> `ALERTING TAMPERED ... DELETED`, plus the heartbeat |
| Disable an alert task | **Heartbeat** within 30 s (`only N of M alert tasks active`). Windows normally logs nothing for a disable; verified on Server 2022 |
| Point a task at different code | Event 4702 -> `... CHANGED to run: <cmd>`, plus the heartbeat checks every task's action |
| Edit or delete bt-alerts.ps1 | Heartbeat compares the file's SHA256 to the hash it held in memory when the window opened |
| Turn auditing off (auditpol) | Event 4719 with "removed" codes on our subcategories -> `AUDITING TURNED OFF`, plus a heartbeat audit-policy check every 5 min (auditpol /backup, numeric column, language independent) |
| Stop the EventLog or Task Scheduler service | Heartbeat checks both every 30 s |
| Clear the Security log | Event 1102 (unchanged) |
| Low-privilege user edits the script (privilege escalation) | `-Install` now locks C:\bt to Administrators + SYSTEM (icacls, by SID). Before v6, C:\bt inherited "Authenticated Users: Modify" from C:\, so any user could have edited a script that SYSTEM runs. |

Heartbeat findings become a normal alert (popup + log), throttled to once per 10 min per issue; repeats show as a red HEARTBEAT line. `-Install` also closes older watch windows so there is only one per box.

Still not covered: killing the watch window (you see it vanish), a kernel-level or Defender-level bypass, or an attacker who silently replaces everything at once while you are not looking. The fix for everything above is the same: `.\bt-alerts.ps1 -Install`.

### 2.12 v6: attack chain

Every alert whose origin is an untrusted IP looks back through the last 400 lines of alerts.log for earlier alerts from the same IP in the last 60 minutes and adds:

- `CHAIN:` the earlier alerts, oldest first. The first line is where the attack started.
- `LIKELY:` a named pattern when one matches. This line also goes in the popup.

| Pattern | LIKELY line |
|---|---|
| Spraying, then a logon from the same IP | a guessed password worked |
| A Kerberoasted account later logs in | its password was cracked |
| Network logon, then a service | PsExec-style remote execution as SYSTEM |
| Network logon, then a task | remote execution / persistence |
| New user, then group add | backdoor admin |
| Several Kerberoast tickets from one IP | Kerberoasting sweep |
| Anything, then log cleared / tampering / auditing off | covering tracks |

`.\bt-alerts.ps1 -Chain <ip>` prints the full story of one IP from the Security log (default 24 h, `-Hours` to change): first seen (the attack start time for the incident report), failed logons and the usernames tried, RC4 Kerberos tickets, first successful login and how, all logins, and every alert from that IP. It works even for activity from before the tool was installed, as long as Windows logged it.

Limit: the chain links by IP. An attacker who switches IPs, or acts as SYSTEM through a webshell, shows up as separate alerts.

New self-test checks: attack chain linking, C:\bt locked down, auditing turned off, alert task disabled.

## 3. whoshere.ps1
One read-only screen:
1. Interactive sessions (`query user`, if present)
2. SMB sessions connected to this box's shares
3. Remote PowerShell (WinRM) sessions: `wsmprovhost.exe` and its owner
4. Successful logons (last N min), grouped by user / type / source IP / process, machine accounts hidden
5. Failed logons grouped by user + source (spraying shows up as a big count from one IP)
6. Established connections grouped by remote IP + process (C2 beacons show up here)
7. Listening ports, with anything outside the usual Windows/AD/web/SQL set in **yellow**
8. **Baseline diff:** `-SaveBaseline` stores admins (by SID), listening ports, all scheduled tasks (including `\Microsoft\*`), services + paths and HKLM Run keys. Later runs print only what's **NEW**, in red.

Save the baseline **after** you've cleaned up, so "normal" means "clean."

## 4. pii-hunt.ps1
Read-only. Report goes to `C:\bt\pii-report.txt`.
1. **Files** in common data/web locations (`-Paths` to override), under 25 MB: Luhn-checked card numbers, US SSNs, DDMMYY-NNNN national IDs, emails, `password=` / `connectionString` strings. Office files are flagged for manual review.
2. **SMB shares**, with Everyone / Authenticated Users / Domain Users access flagged red.
3. **SQL Server** (any instance, Windows auth): logins + sysadmin members, `xp_cmdshell`, every user database's PII-looking columns (card, cvv, ssn, national, passport, license, pass, email, phone, address…) with row counts, and the guest user.
4. **Other databases** (MySQL / MariaDB / Postgres / Mongo services, DB ports listening) flagged for a manual check.

## 5. bt-selftest.ps1
1. **Static checks:** all scripts parse; alert tasks exist and are Ready; whoshere and pii-hunt run.
2. **Live checks** (popups muted, throttles reset): test alert; attack-chain linking (second alert from the same fake IP must list the first); `C:\bt` locked down; create user (plus: origin traced, DO NOW right for the role, only one alert); password reset; re-enable; add to Guests (by SID); 12 failed logons with a real account; scheduled task (command captured); service (4697 alert + duplicate suppressed); Defender exclusion (only if Defender is running); auditing turned off (Kerberos ticket auditing toggled off and back on); alert task disabled (caught by the heartbeat, needs the watch window open, up to 45 s); alert task deleted and restored.
3. **Health:** built-in Guest account (RID 501) disabled?
4. **Manual list:** RDP logon, untrusted-IP network logon, Kerberoasting, log clearing.
5. **On FAIL** it tells you which link broke: Windows didn't log the event (audit/GPO), the task didn't fire, or the script ran but wrote nothing (with the exact debug command).
6. **Cleanup:** removes its user, task and service, and un-mutes popups.

## 6. Competition-day procedure (per box)
1. Change the admin password.
2. Panel `[D]` → `[1]`, or Admin PowerShell → paste `bt-deploy-PASTE.txt` → Enter.
3. Read the backfill's **PRIVILEGED GROUP CHANGES** first.
4. Keep the watch window open. When the scorer shows up as a NETWORK LOGON alert: `-Trust <ip>`.
5. Optional (about 2 min): run `bt-selftest.ps1`.
6. After cleanup: `whoshere.ps1 -SaveBaseline`; re-run `whoshere.ps1` every 15-30 min.
7. On an alert: read FROM/HOW, copy the DO NOW commands, then write the incident report in your own words with timestamps from `alerts.log`.

## 7. Test status

| Box type | Result | Notes |
|---|---|---|
| Server 2022 domain controller (lab) | 25 PASS / 1 FAIL | FAIL = Guest enabled (real finding). Defender SKIP (disabled by a GPO: also a finding). RDP logon alerts seen live during v4. **Untrusted network logon, Kerberoasting and log clearing not yet tested live** (need a second machine / Kali) |
| Server 2022 domain member (lab) | not yet run | expect "domain member server", `net user ... /active:no`, no kerberoast task |
| Server 2012 R2 / 2016 / Win10 / Server Core | not yet run | code avoids PS5-only cmdlets; still needs a real run |

Lessons found by testing (keep these in mind when changing the code):
- `net user` asks Y/N for passwords over 14 characters and hangs a script.
- With Guest enabled, a logon with a **fake** username silently becomes Guest and no 4625 is written; spray tests must use a real user with a wrong password.
- Defender cmdlets error with 0x800106ba when Defender is disabled: detect and SKIP.
- A function named `H` collided with the built-in `h` alias (Get-History). Never reuse alias names.
- `$_` inside a `switch` inside `ForEach-Object` is the switch value, not the pipeline item.
- Windows logs 4702 for task changes but usually not for Disable: the heartbeat is what catches disables.
- QuickEdit pauses a console on click (see 2.7).
- `msg.exe` text is limited to 255 characters.

**Rules notes (INV3 packet):** no rule against bringing your own scripts. Don't paste script output prose or these docs into injects (the AI-detection rule applies to injects). Password changes for scored accounts go through Quotient. The scripts never touch the scoring engine or router.
